# 친구 기능 적용 순서

1. 기존 `202609080001_calendar_accounts.sql`이 적용되어 있어야 합니다. 기존 그룹 SQL은 그대로 유지합니다.
2. Supabase → SQL Editor → New snippet에서 `migrations/202609110001_friends.sql` 전체를 붙여 넣고 Run을 누릅니다.
3. `tests/friends.sql` 전체를 새 쿼리로 실행합니다. 오류 없이 끝나면 테스트를 통과한 것입니다. 이 파일은 임시 사용자 3명을 만들고 마지막에 **ROLLBACK**하므로 부분 실행하지 마세요. 오류가 나면 `rollback;`을 실행하고 오류를 확인하세요.
4. 앱을 새로고침합니다. MY SPACE → 친구에서 자신의 사용자 ID(UUID)를 확인하고 상대에게 전달합니다. 이메일 검색은 제공하지 않습니다.
5. A 계정으로 B의 ID를 검색해 요청합니다. B 계정으로 로그인해 받은 요청을 수락합니다. 두 계정의 친구 목록에서 상대가 보이는지 확인합니다.

## 실제 계정 두 개로 확인

브라우저 일반 창과 시크릿 창을 각각 A/B로 로그인해 사용하세요.

- A: 기존 일정은 그대로 두고 새 개인 일정 하나를 `나만 보기`, 다른 하나를 `친구에게 공개`로 저장합니다. 저장 완료 후 진행합니다.
- B: A의 프로필·캘린더에서 공개 일정만 보이는지 확인합니다. 비공개 일정 날짜에 별도 표시나 개수도 없어야 합니다. 월 이동과 날짜 상세 확인을 합니다. 수정·삭제 버튼은 없습니다.
- A: 공개 일정을 `나만 보기`로 저장합니다. B에서 새로고침하면 즉시 사라져야 합니다.
- A 또는 B: 친구 삭제 후 상대 캘린더를 조회할 수 없어야 합니다. 다시 친구가 되려면 요청과 수락이 필요합니다.
- 그룹 일정은 친구 공개 선택이 비활성화됩니다. 기존 그룹원 공유는 이전과 같습니다.
- DB 권한 테스트는 위 SQL이 직접 비공개 문서 읽기, 대기 중·비친구·삭제된 친구 조회, 그룹 일정 유출, 자기 요청·중복 요청·직접 관계 변경 등을 확인합니다.

## 권한 구조와 주의점

`calendar_accounts`의 소유자 전용 RLS는 변경하지 않습니다. 친구에게 이 테이블의 읽기 정책을 추가하지 마세요. JSON 문서 전체에 비공개 일정이 포함되어 있습니다.

친구 관계는 `moa_friendships`에 저장됩니다. RLS가 켜져 있고 브라우저의 직접 읽기·쓰기 권한은 없습니다. `moa_friends` 함수만 로그인한 호출자의 관계를 확인해 요청/수락/삭제를 수행합니다. 다른 사용자의 ID를 호출자 ID로 지정하는 인자는 없습니다.

캘린더 RPC는 매번 수락된 관계를 확인한 다음 `visibility = friends`인 personal/hobby 일정의 허용된 필드만 반환합니다. 기존 일정(공개 범위 값 없음)은 비공개입니다. group 일정은 데이터에 공개 값이 있어도 반환하지 않습니다. 친구의 일정 원본은 수정할 수 없습니다.

친구 삭제와 비공개 변경은 DB 반영 이후 새 조회부터 적용됩니다. 이미 상대 화면에 내려받은 내용을 원격으로 회수할 수는 없습니다. 앱은 열려 있는 친구 화면을 10초마다 재조회하고, 화면 복귀 및 수동 새로고침 때도 재검증합니다. 네트워크 오류 시 이전 일정은 지웁니다.

이 작업에서는 실제 Supabase 관리자 연결/두 계정 로그인 권한이 없어 **SQL을 원격 DB에 실행하거나 실제 두 계정 검증을 완료하지 않았습니다.** 위 적용과 확인 절차가 필요합니다. 프런트엔드 파일만 배포하면 친구 기능은 DB 설정 안내를 보여줍니다.
